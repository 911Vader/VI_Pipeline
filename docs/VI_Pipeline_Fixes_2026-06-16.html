Part 1 — Pipeline Improvements

Proactive improvements identified by systematic audit of the codebase. None of these caused crashes, but each closed a gap that could cause silent failures, hard-to-debug runs, or incorrect resume behaviour.
Improvement
1. Resume integrity — BAM and VCF validation before skipping steps
analysis/upstream/fastq_handler.py  ·  analysis/upstream/bam_handler.py
Problem

Resume logic only checked Path.exists() and st_size > 0. A BAM truncated mid-write by a crash (e.g., OOM or SIGKILL) would appear valid — DeepVariant would then spend hours on corrupt input before failing.

Fix
  • Added _bam_is_intact(samtools_exe, bam_path) — runs samtools quickcheck which validates the EOF block. A truncated BAM fails instantly; the step is re-run.
  • Added _vcf_has_records(vcf_path) — opens the file (plain or gzipped) and verifies at least one non-header data line exists. A header-only VCF (common crash pattern) is not considered complete.
  • All four resume checkpoints (sorted BAM, dedup BAM, VCF) now use these validators.
+ def _bam_is_intact(samtools_exe: str, bam_path: str) -> bool:
+     result = subprocess.run([samtools_exe, "quickcheck", bam_path], ...)
+     return result.returncode == 0
+
+ def _vcf_has_records(vcf_path: str) -> bool:
+     with open_fn(vcf_path, "rt") as fh:
+         for line in fh:
+             if line and not line.startswith("#"):
+                 return True
+     return False
Improvement
2. BAM QC — samtools flagstat before DeepVariant
analysis/upstream/fastq_handler.py  ·  analysis/upstream/bam_handler.py
Problem

No BAM quality check was run before the multi-hour DeepVariant step. A misaligned or near-empty BAM would only be discovered after DeepVariant failed (or produced a near-empty VCF).

Fix

Added _run_flagstat() which runs samtools flagstat immediately after BAM creation, writes {sample_id}.flagstat.txt, and logs:

  • ERROR if total reads = 0 (alignment produced nothing)
  • WARNING if mapped rate < 70% (likely wrong reference or contamination)

The function never raises — failures are logged, the pipeline continues, and a reviewer can inspect the flagstat file.

Improvement
3. BAM sort-order validation before DeepVariant
analysis/upstream/bam_handler.py
Problem

DeepVariant requires a coordinate-sorted BAM. If a user provided an unsorted BAM via the --bam input path, DeepVariant would fail with a cryptic error deep into the run.

Fix

Added _check_bam_sort_order(samtools_exe, bam_path) which reads the @HD SO: tag from the BAM header and raises a clear RuntimeError immediately if the BAM is not coordinate-sorted.

Improvement
4. LOFTEE — consolidated DEGRADED MODE warning
analysis/annotator.py
Problem

When LOFTEE helper files were missing (human_ancestor_fa, conservation_file), each missing file generated a separate warning at different points in the code. The warnings were easy to miss and gave no overall picture of degradation severity.

Fix

Replaced the scattered per-file warnings with a single consolidated DEGRADED MODE warning issued before the LOFTEE plugin argument is built. The warning lists all missing helpers and their impact on HC/LC classification accuracy in one place.

Bug
5. VEP completion check — header-only file treated as complete
analysis/annotator.py
Problem

The _output_is_complete() function returned True if the VCF had a CSQ header line, even if VEP crashed after writing headers but before writing any variant records. This caused the pipeline to skip re-annotation and feed an empty VCF to the parser — producing zero variants silently.

Fix

Updated _output_is_complete() to require both a valid CSQ header line and at least one non-header data record. A header-only file now correctly returns False, triggering re-annotation.

- return any("CSQ" in line for line in header_lines)
+ has_csq_header = any("CSQ" in line for line in header_lines)
+ has_data = any(not line.startswith("#") for line in lines)
+ return has_csq_header and has_data
Impact: Without this fix, a VEP crash mid-run would be silently masked. The next pipeline run would skip VEP and produce a report with zero variants.
Bug
6. ClinVar benign filter — substring matching caused false positives
analysis/filter_engine.py
Problem

The ClinVar deprioritization check used substring matching on the CLNSIG string. ClinVar values like Conflicting_interpretations_of_pathogenicity contain the substring "pathogenic", which could partially match configured terms. Slash-separated multi-significance values (e.g., Benign/Likely_benign) were matched as a single string rather than as individual components.

Fix

Replaced substring matching with exact set intersection:

  1. Split CLNSIG on / and , to get individual components.
  2. Normalise each component (lowercase, underscores → spaces).
  3. Check if any component is an exact member of the configured exclusion set.
+ components = {
+     part.strip().lower().replace("_", " ")
+     for part in variant.clinvar_significance.replace(",", "/").split("/")
+     if part.strip()
+ }
+ if components & exclude_sigs:
+     # deprioritize
Improvement
7. ACMG classifier — exception tracking and decision trace
analysis/acmg/classifier.py  ·  analysis/parser.py
Problem

When an ACMG rule function raised an exception, it was silently skipped with only a brief log message. There was no way to distinguish "rule evaluated and did not fire" from "rule threw an exception and was skipped". No audit trail was kept on the variant itself.

Fix
  • Added variant.acmg_skipped_rules: List[str] field to the Variant dataclass — populated with codes of rules that errored.
  • Warning log now includes the exception type and message.
  • get_classification_summary() now returns variants_with_rule_errors and rule_error_counts for run-log visibility.
  • Added variant.decision_trace["acmg"] dict recording: rules evaluated, rules triggered, rules skipped due to error, classification, confidence, and all scores used.
Improvement
8. Per-variant decision trace
analysis/filter_engine.py  ·  analysis/acmg/classifier.py  ·  analysis/parser.py
Problem

To understand why a variant was excluded or classified a certain way, a reviewer had to read raw log files. There was no structured per-variant record of which filters fired and which ACMG codes triggered.

Fix

Added variant.decision_trace: dict to the Variant dataclass. Both the filter engine and ACMG classifier now populate it:

  • decision_trace["filter"]: outcome, reason, consequence tier, gnomAD AF used, gene list membership
  • decision_trace["acmg"]: all rules evaluated, triggered codes, skipped codes, classification, confidence, all in-silico scores used

This trace is available in the JSON export for every variant.

Improvement
9. Excluded variants — visible in filter summary
analysis/filter_engine.py
Problem

get_filter_summary() returned only aggregate counts. Excluded variants were invisible without reading thousands of log lines.

Fix

Added top_excluded to the summary dict: the first N excluded variants (default 20) with their coordinates, gene, consequence, gnomAD AF, and exclusion reason. Visible in the run log without log inspection.

Improvement
10. bcftools norm timeout — configurable, default disabled
analysis/vcf_normalizer.py  ·  config/settings.yaml  ·  cli.py
Problem

The bcftools norm step had a hardcoded 2-hour timeout. Large WGS VCFs (e.g., 30× whole-genome) routinely take longer, causing the pipeline to abort with a timeout error rather than running to completion.

Fix
  • Removed the hardcoded timeout. It is now read from settings.yaml under bcftools.norm_timeout_hours.
  • Default is 0 (disabled — no timeout limit), which is safe because bcftools norm will either succeed or fail on its own.
  • Users who want a safety limit can set any positive number of hours.
bcftools:
  norm_timeout_hours: 0   # 0 = no limit (recommended for large WGS VCFs)

11. Pipeline version — single source of truth across all outputs
reporting/__init__.py  ·  json_export.py  ·  pdf_report.py  ·  run_log.py  ·  spreadsheet.py  ·  tsv_export.py
Problem

PIPELINE_VERSION = "1.0.0" was hardcoded independently in three files (json_export.py, pdf_report.py, run_log.py). A version bump required editing three places with no guarantee of consistency. Two output formats (XLSX and TSV) did not embed the version at all.

Fix

  • spreadsheet.py now shows "Pipeline Version" on the XLSX Info sheet.
  • tsv_export.py now writes # VI_Pipeline 1.0.0 as the first comment line.

A version bump now requires changing one line in one file.

Part 2 — Bugs Found and Fixed

Bugs discovered through a deep search of the codebase: running the full test suite, static analysis of logic-dense modules, and reading actual pipeline output from the NIST run.
Logic Bug
A. PP3 rule — REVEL gray zone missing, neutral score cancels damaging vote
analysis/acmg/rules.py — eval_PP3(), lines 289–293
What the bug was

In eval_PP3 (Pathogenic Supporting: multiple in-silico tools predict damaging), REVEL used a binary cutoff: any score below the pathogenic threshold (revel_pathogenic = 0.75) set g1_ben = True, which would cancel a damaging vote from CADD in the same correlated group.

This is wrong. REVEL scores between revel_benign (0.15) and revel_pathogenic (0.75) are in a gray zone — they carry no signal in either direction. A gray-zone score should be neutral, not actively cancel a damaging signal from another tool.

The sister function eval_BP4 (Benign Supporting) already implemented the correct three-zone logic for REVEL. The eval_PP3 function was asymmetric.

Concrete example of wrong output
ScoreValueZone
CADD phred30Damaging (≥ 20 threshold)
REVEL0.50Gray zone (0.15–0.75)
SpliceAI0.60Damaging (≥ 0.50 threshold)

Before fix: REVEL=0.50 set g1_ben=True, canceling the CADD damaging vote → Group 1 vote = None. Only SpliceAI (Group 2) voted damaging. 1 group < 2 required → PP3 = False (incorrect).

After fix: REVEL=0.50 is gray zone → no change to g1_ben. CADD vote stands. Group 1 (CADD) + Group 2 (SpliceAI) = 2 groups → PP3 = True (correct).

Code change
  if variant.revel_score is not None:
      if variant.revel_score >= t["revel_pathogenic"]:
          g1_dam = True
-     else:
-         g1_ben = True
+     elif variant.revel_score <= t["revel_benign"]:
+         g1_ben = True
+     # Gray zone (revel_benign < score < revel_pathogenic): no signal
+     # A neutral REVEL score must not cancel a CADD damaging vote.
Impact: Variants with intermediate REVEL scores (common in missense variants) combined with high CADD and another damaging tool were being under-classified. PP3 was silently suppressed, reducing the final ACMG pathogenicity classification of affected variants. Two new regression tests were added to document the correct behavior.
Test Bug (×2 root causes, 6 failures)
B. Test failures — missing subprocess mocks in fastq_handler tests
tests/analysis/upstream/test_fastq_handler.py
Root cause 1 — pigz detected at runtime, forcing shell mode

TestRunBwaAlign._call() patched subprocess.Popen and subprocess.run but did not mock shutil.which("pigz"). Since pigz is installed on this server, _run_bwa_align always took the shell path (a single bash command with set -o pipefail), which collapses the BWA and samtools sort exit codes into one combined return code.

The tests expected separate per-process error messages ("BWA alignment failed" vs "samtools sort failed"), but in shell mode both are reported identically. Two tests failed:

  • test_bwa_nonzero_raises_runtime_error — got "BAM not produced" instead of "BWA alignment failed"
  • test_sort_nonzero_raises_runtime_error — got "BWA alignment failed" instead of "samtools sort failed"

Fix: Added patch("analysis.upstream.fastq_handler.shutil.which", return_value=None) to _call() to force the Popen code path where per-process exit codes are independent.

Root cause 2 — _run_seqkit_pair and _run_markdup not mocked

TestRunFastqToVcf._run_success() mocked _run_bwa_align, _run_samtools_index, and _run_deepvariant, but run_fastq_to_vcf also calls:

  • _run_seqkit_pair — FASTQ pair synchronisation, runs before BWA. Since shutil.which was globally mocked to return /usr/bin/bwa, this called /usr/bin/bwa pair ... → failed with "unrecognized command".
  • _run_markdup — duplicate marking, runs after BWA. Tried to run sambamba markdup (the default tool) → failed.

Four tests failed because the pipeline never reached the mocked steps.

Fix: Added _run_seqkit_pair and _run_markdup mocks to _run_success() and the two individual failing integration tests.

Investigated — No Bug
ClinVar parsed from CSQ field vs INFO field
analysis/parser.py
Concern

The parser reads ClinVar significance from primary.raw (the per-transcript CSQ dict), with a comment claiming VEP embeds it there via --custom. Standard VEP documentation suggests --custom fields go into the VCF INFO column as standalone entries, not into the CSQ string. If the comment was wrong, all ClinVar data would be silently None.

Verification

Inspected the actual VEP-annotated VCF from the NIST HG001 run (HG001.norm.vep.vcf). The CSQ format header line ends with: 

...LoF|LoF_filter|LoF_flags|LoF_info|ClinVar|ClinVar_CLNSIG|ClinVar_CLNREVSTAT|ClinVar_CLNDN

ClinVar fields ARE embedded inside the CSQ string. VEP does inject them into CSQ when using --custom with --vcf output. The standalone ##INFO=<ID=ClinVar_CLNSIG,...> headers also appear but as secondary copies. The parser reading from primary.raw is correct.
