Why More Threads ≠ More Speed

A visual explanation of thread scaling, Amdahl's Law, and why minibwa saturates at ~32 threads.

1 — The Core Promise vs The Reality

When people say "use more threads," they imagine perfect parallel scaling: 2× threads = 2× speed, 4× threads = 4× speed. Reality is always worse because not all parts of the program can run in parallel.

The observed behaviour on this server: Running BWA-MEM with 192 threads showed 4,623% CPU in htop — that's only ~46 effective cores. 146 threads were fighting over internal locks instead of doing alignment work.

2 — Amdahl's Law: The Serial Bottleneck

Every program has a serial fraction — work that must happen one step at a time (reading the genome index, writing output, coordination logic). No matter how many threads you add, you cannot speed up the serial part.

Amdahl's Law: Maximum speedup = 1 / (serial fraction + parallel fraction ÷ threads)

Key insight: With just 10% of the program being serial, the maximum possible speedup with infinite threads is only 10×. With 5% serial, the ceiling is 20×. The serial bottleneck always wins eventually.

3 — Lock Contention: Threads Waiting for Each Other

BWA-MEM and minibwa use a shared FM-index (the compressed genome lookup table). When one thread searches the index, it takes a lock — other threads must wait. As you add more threads, more of them are waiting rather than working.

4 — minibwa Thread Saturation

minibwa is faster per-thread than the old BWA (better SIMD vectorisation, tighter memory access patterns). But it has the same fundamental bottleneck: the shared genome index. It saturates around 32 threads — beyond that, adding threads gives almost no extra speed.

32 threads
Why not just use 1 thread then? Threads still help enormously up to the saturation point — going from 1 to 32 threads gives a real ~18× speedup. The problem is only going past the saturation point. That's why the pipeline is set to bwa_threads: 32, not 1 and not 192.

5 — Where minibwa's Speedup Actually Comes From

The speedup over old BWA-MEM comes from doing more useful work per thread, not from using more threads.

The key difference: minibwa uses AVX-512 SIMD instructions to process 16 bases at once per CPU operation (vs 4 in old BWA). It also uses a more compact index format (.mbw + .l2b) that fits better in CPU cache. Each thread does more work per clock cycle — so at 32 threads, it finishes the same job in less time.

So "4× faster" means: at the same thread count, each thread is ~4× more efficient. Not that you can use 4× fewer threads to get the same time — though you can use fewer threads and still beat old BWA.
