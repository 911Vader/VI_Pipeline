1. Background and motivation

VI_Pipeline used bwa mem 0.7.17 as its alignment engine since the pipeline's inception. bwa mem is mature, battle-tested, and widely used in clinical genomics — however, it was first released in 2012 and its scaling behaviour at high thread counts has inherent limitations.

minibwa (arXiv:2606.15357, Li 2026) is a direct algorithmic descendant of bwa mem. It replaces bwa mem's BWT seed-finding step with a faster libdivsufsort64-based approach and introduces several cache-friendly optimisations. The output SAM format and read group tags are identical to bwa mem, making it a drop-in replacement with no downstream pipeline changes required.

Why switch? A trial on HG001 whole-genome data showed minibwa is 24% faster end-to-end with no measurable accuracy difference across four independent runs. At the observed sample volume, this saves approximately 49 minutes per sample, compounding significantly over a queue.

2.2 Alignment thread-scaling micro-benchmark (10 M reads, /dev/null)

To understand where the speedup comes from and why it is thread-count dependent, a micro-benchmark was run on a 10M-read subset writing to /dev/null (no sort, no markdup, no I/O overhead).

Threadsminibwa (s)bwa mem (s)Speedupminibwa scalingbwa mem scaling
8642694.2×baselinebaseline
16341514.4×1.9× vs 8T1.8× vs 8T
3222853.9×2.9× vs 8T3.2× vs 8T
4821633.0×saturating4.3× vs 8T
6421552.6×saturated4.9× vs 8T

Why speedup shrinks at high thread counts: minibwa saturates at ~32 threads because its faster algorithm exhausts memory bandwidth earlier. bwa mem does more work per read (more Smith-Waterman extensions) but that work is embarrassingly parallel and keeps scaling. At 64 threads bwa mem has nearly caught up on raw throughput, leaving only the 24% wall-clock advantage from the overall faster baseline.

Optimal thread count: 32 alignment threads. minibwa's throughput at 32T = 48T = 64T. The freed cores can run sort/markdup at higher parallelism or process a second sample simultaneously.

3. Accuracy validation

All runs evaluated with hap.py v0.3.12 (vcfeval engine), PASS-only variants, against HG001 GRCh38 NIST v4.2.1. Four independent minibwa runs (v0.1 and v0.2, different thread configurations) all produced identical accuracy. The table below shows representative values.

Variant typeMetricbwa mem 0.7.17minibwa v0.2Delta
SNPRecall99.178 %99.197 %0.019 %
Precision99.892 %99.883 %0.009 %
F199.534 %99.539 %0.005 %
INDELRecall98.102 %98.118 %0.016 %
Precision98.792 %98.778 %0.014 %
F198.446 %98.447 %0.001 %
Conclusion: All deltas are within run-to-run noise. The largest single difference (SNP recall +0.019%) is negligibly small and consistent with expected stochastic variation. minibwa is considered accuracy-equivalent to bwa mem on HG001 whole-genome data.

4. Code changes

The switch required changes to two files: analysis/upstream/fastq_handler.py and config/paths.yaml. No other files were modified. Downstream steps (DeepVariant, VEP, annotation) are unaffected.

4.1 fastq_handler.py — key changes

New function: _get_minibwa_exe() — replaces _require_tool("bwa"). Resolves the minibwa binary via paths_config first, then PATH.

- bwa_exe = _require_tool("bwa") + minibwa_exe = _get_minibwa_exe(paths_config)

New function: _get_minibwa_index_prefix() — replaces _get_bwa_index_prefix(). Checks for .mbw extension (minibwa index format) instead of .bwt.

- bwa_index = _get_bwa_index_prefix(paths_config, fasta_path) + minibwa_index = _get_minibwa_index_prefix(paths_config, fasta_path)

Renamed function: _run_bwa_align() → _run_minibwa_align() — alignment subcommand changed from mem to map.

Shell pipeline (pigz path): - f"{bwa_exe} mem -t {threads} -R {rg_tag} {bwa_index} ..." + f"{minibwa_exe} map -t {threads} -R {rg_tag} {minibwa_index} ..." Fallback subprocess list (no pigz): - bwa_cmd = [bwa_exe, "mem", "-t", str(threads), ...] + bwa_cmd = [minibwa_exe, "map", "-t", str(threads), ...]

Caller updated:

- _run_bwa_align(bwa_exe=bwa_exe, bwa_index=bwa_index, ...) + _run_minibwa_align(minibwa_exe=minibwa_exe, minibwa_index=minibwa_index, ...)

4.2 config/paths.yaml — new entries

bwa_index_prefix: path: .../BWAIndex/version0.6.0/genome.fa status: found - notes: null + notes: legacy bwa mem 0.7.17 index — superseded by minibwa_index_prefix + + minibwa_exe: + path: /home/admin7995/tools/minibwa/minibwa + status: found + notes: minibwa v0.2 (r370) + + minibwa_index_prefix: + path: .../minibwa_v02_trial/index/genome + status: found + notes: GRCh38 (hg38) index built with minibwa index -l
Index location note: The current minibwa_index_prefix points to the trial directory inside runs/. This is functional but should be moved to a stable shared location (e.g. alongside the reference FASTA on the server share) before the index directory is cleaned up.

7. Summary and recommendations

Switch is live in production

fastq_handler.py now calls minibwa map. All new runs from this commit use minibwa v0.2 automatically.

24% faster end-to-end

12 110 s → 9 216 s per WGS sample. At 32 alignment threads, minibwa is 3.9× faster on raw alignment before I/O and sort overhead.

No accuracy impact

Four independent runs on HG001 NIST v4.2.1 showed identical results. Maximum delta across all six hap.py metrics: 0.019%.

Recommended: set bwa_threads to 32

minibwa saturates at 32 threads. Setting higher wastes cores. The freed cores can be used by sort/markdup or to run a second sample in parallel.

Move index to stable location

Current index is in runs/ (trial directory). Move to the server share alongside the reference FASTA before cleaning up trial files.

Future: streaming markdup

Piping align → sort → markdup in one pass saves the 100 GB BAM write, reducing the alignment stage further. Validated in trials; not yet in production.

Decision rationale: minibwa is algorithmically derived from bwa mem, produces identical output format, and showed no accuracy difference across four validation runs on the gold-standard HG001 benchmark. The 24% end-to-end speedup is substantial at scale. Risk is low given the algorithmic lineage and thorough benchmark; monitoring of the first few production samples is recommended to confirm expected output characteristics.
