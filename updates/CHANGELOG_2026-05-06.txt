VI_Pipeline — Change Log
Date: 2026-05-06
================================================================================

SUMMARY
-------
4 fixes and improvements: FASTQ multi-allelic normalization was missing,
stale annotated VCF could be silently reused after a failed run, the GUI
had no progress indicator, and the run log was not selectable or copyable.
Full path audit confirmed all 44 pipeline dependencies are present.

================================================================================

1. FASTQ PATH MISSING NORMALIZATION STEP
File: cli.py

Problem:
  When input was a FASTQ, the pipeline ran BWA + DeepVariant to produce a
  raw VCF, then passed it directly to VEP without checking for multi-allelic
  records. DeepVariant commonly outputs multi-allelic records (e.g.
  REF=ACC, ALT=A,AC). The VCF path already had this check and normalised
  via bcftools norm before annotation; the FASTQ path did not.
  Result: the parser crashed with:
    ValueError: Multi-allelic variant at chr1:1257393 (REF=ACC, ALT=A,AC).

Changes:
  - Added the same has_multiallelic_records() + normalize_vcf() check to
    the FASTQ path, immediately after run_fastq_to_vcf() returns
  - If multi-allelic records are detected, bcftools norm splits them into
    biallelic records before VEP annotation
  - If the VCF is already biallelic, normalization is skipped (no overhead)
  - Deleted the stale SUD58_updt.vep.vcf left by the failed run so that
    re-annotation runs cleanly on the next attempt

--------------------------------------------------------------------------------

2. STALE ANNOTATED VCF REUSE AFTER FAILED RUN
File: cli.py

Problem:
  Both VCF and FASTQ paths used {sample_id}.vep.vcf as the annotated output
  name regardless of whether normalization was applied. With
  skip_if_annotated_exists: true, if a previous run had completed VEP on an
  un-normalized input and then failed at parsing, a re-run would detect the
  old annotated VCF, skip VEP, and crash at parsing again — indefinitely.

Changes:
  - When normalization is applied, the annotated VCF is now written to
    {sample_id}.norm.vep.vcf instead of {sample_id}.vep.vcf
  - A pre-normalization annotated VCF (vep.vcf) is therefore never mistaken
    for the output of a normalized run (norm.vep.vcf)
  - Applies to both VCF and FASTQ input paths

--------------------------------------------------------------------------------

3. GUI PROGRESS TRACKING (Stage bar + elapsed timer)
Files: cli.py, analysis/upstream/fastq_handler.py, gui/app.py

Problem:
  The GUI gave no indication of how far through the pipeline a run was.
  During multi-hour VEP annotation or BWA alignment, the status bar showed
  only "Running..." with no further detail.

Changes:

  cli.py:
  - Added _stage(step, total, label) function that emits structured markers:
      ##STAGE## n/N Description
    These are parsed by the GUI and are invisible in normal CLI usage.
  - Added _Prog class (local to main()) that tracks current step and total,
    and calls _stage() before each pipeline step.
  - Stage counts are determined before the first stage is emitted by running
    the fast pre-checks (has_csq_annotation, has_multiallelic_records) up
    front. This means the progress bar shows the correct total from step 1.

  Stage totals by input type:
    VCF pre-annotated          5 stages  parse→filter→classify→rank→reports
    VCF unannotated            6 stages  VEP + 5 above
    VCF unannotated + norm     7 stages  norm→VEP + 5 above
    FASTQ                      8 stages  BWA→DV→VEP + 5 above
    FASTQ + norm               9 stages  BWA→DV→norm→VEP + 5 above

  analysis/upstream/fastq_handler.py:
  - Added optional stage_callback parameter to run_fastq_to_vcf()
  - Callback fires between BWA completion and DeepVariant start, allowing
    cli.py to emit separate "Aligning reads" and "Calling variants" stage
    markers for the two slow FASTQ sub-steps.

  gui/app.py:
  - Added ttk.Progressbar (determinate, 0–100) below the Run/Stop buttons
  - Added stage label: "Step N of M  —  Running VEP annotation"
  - Added elapsed time label: "Elapsed: 00:23:41" (ticks every second)
  - _poll() detects ##STAGE## lines, updates the bar, and logs a clean
    "▶ Step N of M — label" line in the run log panel
  - Timer starts when Run is pressed, stops on completion or stop
  - On success: bar reaches 100%, stage label shows "Complete"
  - On stop/failure: timer stops, bar stays at last reached stage

4. RUN LOG NOT SELECTABLE OR COPYABLE
File: gui/app.py

Problem:
  The run log ScrolledText widget used state=tk.DISABLED to prevent editing.
  On Linux/GTK, DISABLED state blocks all mouse interaction including text
  selection. Users could not select or copy any text from the log panel.

Changes:
  - Removed state=tk.DISABLED from the log widget constructor
  - Widget stays in NORMAL state permanently (required for mouse selection
    on Linux)
  - Added a <Key> binding that intercepts keyboard events:
      Ctrl+anything  → allowed  (Ctrl+C copy, Ctrl+A select-all, etc.)
      Navigation keys (arrows, Home, End, Page Up/Down)  → allowed
      All other keys  → blocked (returns "break")
  - <<Paste>> event bound to "break" (paste blocked)
  - _log_line() and _clear_log() no longer need to toggle state:
    state toggle calls removed from both methods
  - Right-click Copy / Select All menu (already present) continues to work
