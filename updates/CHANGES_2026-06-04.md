## 1. Corrupted R1 Download — Diagnosis and Fix

### What happened
The first download attempt used `lftp pget -n 16` for R1 and R2 **simultaneously** — 32 total
connections to ENA's FTP server. ENA began refusing connections. When we tried to stop and
restart with fewer connections, `pkill` silently failed (exit code 144). The old lftp processes
kept running in the background.

A new lftp process was then started for the same output file. Two separate lftp processes were
now writing to different byte positions in the same file at the same time — neither knowing the
other existed. The file reached 48 GB and appeared to complete, but the MD5 checksum was wrong:

```
Expected: 63634f9d0736e09debdfe5827a5e82a0
Got:      d53a165d5e0763b3ddb0a52ff4ee583c
```

### Root cause
Concurrent writes to the same file from two independent lftp instances → data corruption.

### Fix applied
1. Processes killed by explicit PID (not pkill) — guaranteed termination
2. Corrupted R1 deleted along with its `.lftp-pget-status` file
3. Downloads made **sequential** — R1 completes and is verified before R2 starts
4. MD5 checksum verified after each file — catches corruption before the file is used

## 2. Switched to fasterq-dump (NCBI SRA)

### Why
ENA FTP (`ftp.sra.ebi.ac.uk`) throttles downloads to ~1 MB/s per IP regardless of thread count.
At that speed, the two FASTQ files (51 GB + 53 GB = 104 GB total) would take ~25 hours.

NCBI's SRA toolkit routes downloads through AWS/GCP infrastructure, delivering significantly
higher throughput. The same data (ERR194147) is mirrored on both ENA and NCBI SRA.

### How fasterq-dump works

| Phase | What it does |
|-------|-------------|
| **lookup** | Downloads SRA data from NCBI cloud, builds a read-position index |
| **merge** | Sorts reads into temporary chunk files (`bg_sub_*.dat`) |
| **join** | Matches each R1 read with its R2 mate using read IDs |
| **concat** | Writes final `ERR194147_1.fastq` and `ERR194147_2.fastq` |

After fasterq-dump completes, `pigz -p 16` compresses both files to `.fastq.gz` automatically.

### Command used
```bash
fasterq-dump ERR194147 \
    --split-files \
    --threads 16 \
    --outdir /mnt/server_share/Reference_Material/validation/NA12878 \
    --temp   /mnt/server_share/Reference_Material/validation/NA12878/tmp
```

### Status (as of end of day)
- Lookup: complete
- Merge: complete
- Join: in progress (~5% when last checked)
- Output: `ERR194147_1.fastq` and `ERR194147_2.fastq` not yet written (written at end of join)

## 4. Pipeline Thread Configuration — Maximised for This Server

**Server specs:** 192 CPUs · 1 TB RAM

Changes in `config/settings.yaml`:

| Parameter | Before | After | Effect |
|-----------|--------|-------|--------|
| `deepvariant.bwa_threads` | 32 | **64** | BWA alignment ~2× faster (~10–20 min for 30× WGS) |
| `deepvariant.num_shards` | 4 | **64** | DeepVariant ~16× faster (~20–40 min for 30× WGS) |
| `vep.fork` | 64 | 64 | Already optimal — unchanged |

### Why not 192 threads for everything?
- **BWA at 64**: returns diminishing gains past ~64 threads; disk I/O becomes the bottleneck
- **DeepVariant at 64**: each shard uses ~4–8 GB RAM; 64 shards = ~256–512 GB, safely within 1 TB
